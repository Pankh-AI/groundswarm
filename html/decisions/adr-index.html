Decisions

Architecture and licensing decisions made so far, and what's still open
ADR-001 Decided

Base the worker runtime on OpenClaw, don't build a new agent runtime

Groundswarm workers are OpenClaw instances (github.com/openclaw/openclaw, MIT-licensed), not a new distribution/channel layer built from scratch.

Why: OpenClaw already solves distribution to WhatsApp, Slack, Discord, Telegram and iMessage through its Gateway and channel connectors, and it's genuinely open (MIT), unlike the SwarmBench Harbor task-package conventions this project must not reuse. Groundswarm does not modify or relicense OpenClaw itself.

ADR-002 Decided

Name the project "Groundswarm", not anything Claude-adjacent

Rejected names in the "SwarmClaw" / "AgentSwarm-as-Claude-pun" family.

Why: Anthropic sent OpenClaw's creator a cease-and-desist over its original "Clawd" branding (2026-01-27) specifically over Claude-adjacent naming. Building on OpenClaw already carries some inherited brand risk; compounding it with a Claude-adjacent project name was an avoidable mistake. Name-availability check (GitHub/npm/PyPI/domains) came back clear, see similar-projects research.

ADR-003 Decided

Open-core licensing: Apache-2.0 core, separate future paid Enterprise edition

Groundswarm's own code (orchestrator + verifier) ships under Apache License 2.0, free for individuals and organizations of any size. A future, separate "Groundswarm Enterprise" edition (SSO, audit/compliance reporting, managed hosting, support SLAs) is planned under a commercial license; the core engine is never gated behind it.

Why: matches the closest credible precedent found in the market survey (DeepEval / Confident AI's open-core model) rather than a source-available/BSL-style license, which avoids both the legal complexity and the community-trust friction that relicensing disputes have caused elsewhere in this space.

ADR-004 Decided

Copyright holder: Pankh-AI

LICENSE now reads Copyright 2026 Pankh-AI.

Why: published as company work under the Pankh-AI org rather than an individual contributor, both to reflect where the work actually happens and so the project can be claimed as Pankh-AI's going forward. ADR-005 Open

First proof-case domain

README currently proposes vendor infrastructure incident monitoring (the same domain the grounding pattern was proven on in the capstone) as the first real Groundswarm use case, marked explicitly as "proposed, open to change."

Why open: not yet confirmed or overridden.

ADR-006 Decided

Orchestrator and verifier implementation language: Python

New Groundswarm code (orchestrator + verifier) is Python, not Rust.

Why: the proven capstone verifier is already Python and directly reusable rather than a rewrite; every framework and eval tool surveyed in the market research (AutoGen, LangGraph, CrewAI, swarms, camel-ai, OpenHands, DeepEval, Ragas) is Python-first, maximizing contributor overlap with exactly the ecosystem this project draws from; and the actual workload (LLM calls, live source re-fetching) is I/O-bound, not CPU-bound, so Rust's performance edge would not show up in practice. A narrow hot path can get a targeted extension later if one is ever actually needed.

ADR-007 Decided: build it. Confirmed gap, not yet implemented

Add Memory as a fourth component: a scoped, verified shared knowledge store

Fourth component alongside Workers, Orchestrator and Verifier, entries scoped by validity/blast radius (org-wide / team / project / single-run) rather than by which worker wrote them, gated by a deterministic pre-merge validator rather than trust in the last writer, tiered always-loaded-vs-on-demand retrieval as an explicit token-cost budget, and explicit TTL / supersedes staleness handling. Drafted into README.

Why: reuses the verifier's own trust primitive (deterministic gate first, fail closed on ambiguity) applied to the swarm's shared knowledge instead of its task output, a coherent extension rather than a bolted-on feature. Generalized from operating a real single-user instance of the same pattern across many long-lived projects, not from a graded benchmark the way the verifier's pattern was.

Competitive check, done: checked against Mem0, Letta, Zep/Graphiti, LangMem, CrewAI, Cognee, Mastra, AWS Bedrock AgentCore Memory, and Google Vertex Memory Bank, plus two 2026 research proposals. No product or proposal combines all five properties; each solves one piece (Letta's tiering, Graphiti's bi-temporal staleness, LangGraph's TTL, memorywire's human-review channel) and leaves the rest to the app developer or an LLM's judgment. Sharper still: a 2026 fact-conflict benchmark scored Mem0 at 18% and Zep/Graphiti at 7%, both lean on an LLM to decide whether a new fact supersedes an old one, and both measurably fail at it most of the time, direct evidence for the deterministic-gate choice, not just an assumption. Full writeup: memory landscape research.

ADR-008 Decided

Publish under the Pankh-AI GitHub org, as its own isolated repo

Groundswarm publishes as company work under an existing Pankh-AI GitHub org, not an individual account. The Pankh-AI org already has other repos on it, possibly including private ones.

Verified locally: groundswarm/ is currently untracked inside this Research working directory, which is a single git repository (37 commits, no remote configured) that also contains kaggriculture's live competition strategy and other private research. Zero commits reference groundswarm/ so far, and its README/LICENSE/html contain no references to any other project in this workspace.

Why this matters: Research itself must never get a remote, public or otherwise, its history alone would expose unrelated private work regardless of what folder someone meant to publish. Groundswarm has to become its own freshly-initialized repository in a separate location before anything is pushed anywhere.

Before the first push (unverified locally, needs a human check on GitHub): confirm the Pankh-AI org's default new-repo visibility setting so Groundswarm doesn't inherit a stricter or looser default than intended, and confirm no org-wide Actions secrets are configured in a way a public repo's workflows could read, before any CI is wired up for this repo.
