Decisions

Architecture and licensing decisions made so far, and what's still open
ADR-001 Decided

Base the worker runtime on OpenClaw, don't build a new agent runtime

Groundswarm workers are OpenClaw instances (github.com/openclaw/openclaw, MIT-licensed), not a new distribution/channel layer built from scratch.

Why: OpenClaw already solves distribution to WhatsApp, Slack, Discord, Telegram and iMessage through its Gateway and channel connectors, and it's genuinely open (MIT), unlike the SwarmBench Harbor task-package conventions this project must not reuse. Groundswarm does not modify or relicense OpenClaw itself.

ADR-002 Decided

Name the project "Groundswarm", not anything Claude-adjacent

Rejected names in the "SwarmClaw" / "AgentSwarm-as-Claude-pun" family.

Why: Anthropic sent OpenClaw's creator a cease-and-desist over its original "Clawd" branding (2026-01-27) specifically over Claude-adjacent naming. Building on OpenClaw already carries some inherited brand risk; compounding it with a Claude-adjacent project name was an avoidable mistake. Name-availability check (GitHub/npm/PyPI/domains) came back clear, see similar-projects research.

ADR-003 Decided

Open-core licensing: Apache-2.0 core, separate future paid Enterprise edition

Groundswarm's own code (orchestrator + verifier) ships under Apache License 2.0, free for individuals and organizations of any size. A future, separate "Groundswarm Enterprise" edition (SSO, audit/compliance reporting, managed hosting, support SLAs) is planned under a commercial license; the core engine is never gated behind it.

Why: matches the closest credible precedent found in the market survey (DeepEval / Confident AI's open-core model) rather than a source-available/BSL-style license, which avoids both the legal complexity and the community-trust friction that relicensing disputes have caused elsewhere in this space.

ADR-004 Decided

Copyright holder: Pankh-AI

LICENSE now reads Copyright 2026 Pankh-AI.

Why: published as company work under the Pankh-AI org rather than an individual contributor, both to reflect where the work actually happens and so the project can be claimed as Pankh-AI's going forward. Confirmed directly, not inferred, the local git identity on this machine never matched the name this project should be published under and was deliberately not used.

ADR-005 Decided

First proof-case domain: vendor infrastructure incident monitoring

Confirmed as the first real Groundswarm use case, no longer "proposed, open to change": a swarm of workers each reads a vendor's public incident postmortems, extracts and classifies findings, and the verifier confirms every claim against the live source before it reaches a risk briefing a real team could act on.

Why this domain, not left open any longer: it's not a fresh choice being made now, it's the domain every measured result in this repo already ran against — the original capstone prototype, Move 2 (ADR-017), the 1x–200x N-worker sweep (ADR-015), the OpenClaw feedback loop (ADR-019), and the CLI harness calibration (ADR-020) all used incident-monitoring sources. Confirming it formally just names what the evidence already committed to, so the public-facing pitch (README, landing page) can point at one concrete demo instead of hedging on the use case while citing results from it.

ADR-006 Decided

Orchestrator and verifier implementation language: Python

New Groundswarm code (orchestrator + verifier) is Python, not Rust.

Why: the proven capstone verifier is already Python and directly reusable rather than a rewrite; every framework and eval tool surveyed in the market research (AutoGen, LangGraph, CrewAI, swarms, camel-ai, OpenHands, DeepEval, Ragas) is Python-first, maximizing contributor overlap with exactly the ecosystem this project draws from; and the actual workload (LLM calls, live source re-fetching) is I/O-bound, not CPU-bound, so Rust's performance edge would not show up in practice. A narrow hot path can get a targeted extension later if one is ever actually needed.

ADR-007 Decided: build it. Confirmed gap, not yet implemented

Add Memory as a fourth component: a scoped, verified shared knowledge store

Fourth component alongside Workers, Orchestrator and Verifier, entries scoped by validity/blast radius (org-wide / team / project / single-run) rather than by which worker wrote them, gated by a deterministic pre-merge validator rather than trust in the last writer, tiered always-loaded-vs-on-demand retrieval as an explicit token-cost budget, and explicit TTL / supersedes staleness handling. Drafted into README.

Why: reuses the verifier's own trust primitive (deterministic gate first, fail closed on ambiguity) applied to the swarm's shared knowledge instead of its task output, a coherent extension rather than a bolted-on feature. Generalized from operating a real single-user instance of the same pattern across many long-lived projects, not from a graded benchmark the way the verifier's pattern was.

Competitive check, done: checked against Mem0, Letta, Zep/Graphiti, LangMem, CrewAI, Cognee, Mastra, AWS Bedrock AgentCore Memory, and Google Vertex Memory Bank, plus two 2026 research proposals. No product or proposal combines all five properties; each solves one piece (Letta's tiering, Graphiti's bi-temporal staleness, LangGraph's TTL, memorywire's human-review channel) and leaves the rest to the app developer or an LLM's judgment. Sharper still: a 2026 fact-conflict benchmark scored Mem0 at 18% and Zep/Graphiti at 7%, both lean on an LLM to decide whether a new fact supersedes an old one, and both measurably fail at it most of the time, direct evidence for the deterministic-gate choice, not just an assumption. Full writeup: memory landscape research.

ADR-008 Decided

Publish under the Pankh-AI GitHub org, as its own isolated repo

Groundswarm publishes as company work under an existing Pankh-AI GitHub org, not an individual account. The Pankh-AI org already has other repos on it, possibly including private ones.

Verified locally: groundswarm/ is currently untracked inside this Research working directory, which is a single git repository (37 commits, no remote configured) that also contains kaggriculture's live competition strategy and other private research. Zero commits reference groundswarm/ so far, and its README/LICENSE/html contain no references to any other project in this workspace.

Why this matters: Research itself must never get a remote, public or otherwise, its history alone would expose unrelated private work regardless of what folder someone meant to publish. Groundswarm has to become its own freshly-initialized repository in a separate location before anything is pushed anywhere.

Before the first push (unverified locally, needs a human check on GitHub): confirm the Pankh-AI org's default new-repo visibility setting so Groundswarm doesn't inherit a stricter or looser default than intended, and confirm no org-wide Actions secrets are configured in a way a public repo's workflows could read, before any CI is wired up for this repo.

ADR-009 Decided: built

Add a third verification method for computed claims: independent arithmetic, not a quote match or an LLM judge

The Verifier gained a third path (verifier/arithmetic.py + Verifier._check_computation), selected whenever a Claim carries a computation payload instead of a plain quote: each operand is quote-round-trip checked into the source exactly like today's deterministic path, then the arithmetic itself (currently duration_minutes, sum, difference) is independently recomputed in Python and compared to what the worker claimed. Unsupported operations or unparseable operands fail closed to unverified, same discipline as the judge path. Separately, checks.py's _normalize() now folds curly quotes/dashes/ellipsis to their plain-ASCII equivalents before comparing.

Why: the 55-worker rejection analysis found two real content errors in 234 verified claims that the original two-path verifier (quote match, LLM judge) could not have caught on principle: a worker asserted a 41-minute source-derived duration as "17 minutes," and a worker wrote a curly apostrophe where the source has a straight one, sinking an otherwise word-for-word correct quote. An LLM judge re-reasoning about arithmetic is exactly as unreliable as the worker that produced it in the first place — both are the same class of model making the same class of mistake — so this is a genuine third method, not the judge path in disguise: it fails closed the moment a number can't be independently recomputed, rather than asking a model whether the number "looks right."

Scope: deliberately narrow — three operations covering the patterns actually observed (timestamp deltas, sums, differences), not a general math verifier. The extraction worker's system prompt (sim_worker.py) now also explicitly forbids echoing the schema's own field-description text into the quote field, the single largest failure mode found (10 of 29 rejections) — not yet re-validated against a live swarm run to see how reliably dolphin3 follows the new instruction.

ADR-010 Decided

Sequencing: re-validate the fix, then build a benchmark, then Memory — not the reverse

Three moves, in order, gating each on the previous one's result rather than running them in parallel:

1. Re-validate the ADR-009 fix before claiming it worked. Same 55-worker corpus, same config, only the code changed — compare raw rejection rate, fabrication catch rate, false vs. true rejections, quote-format vs. computation vs. other failure counts, and token/latency overhead against the archived pre-fix run. A worker-count sweep (1/5/20/55/100+) is a genuinely larger compute commitment on a single local Ollama instance and is scoped separately, gated on what this result shows.

2. Build a Groundswarm benchmark before Memory. The actual claim under test isn't "we have a verifier," it's "Groundswarm produces fewer unsupported factual claims than an ordinary agent swarm while preserving useful answers," scored at the atomic claim level: supported / unsupported / unverifiable / incorrect computation / wrong attribution / omitted, against a single agent and the same swarm with verification disabled as controls.

3. Only then build Memory, and not as a vector-DB bolt-on: every entry carries its evidence (source id/version/span/retrieval time), its derivation (extractor, computation if any, dependencies), its verification (method, verdict, timestamp), and a state (VERIFIED / STALE / CONFLICTED / REJECTED) — so trust propagates source → claim → derived claim → memory → future answer, instead of resetting at each hop.

Why this order: Memory enlarges the attack surface (more write paths, more staleness states, more places a bad claim can hide) before the base extraction-and-verification primitive is proven to actually work end to end. Building Memory first would mean building a bigger, harder thing on top of a foundation whose real failure rate wasn't yet measured. The benchmark is more valuable than Memory at this stage because "we have a verifier" isn't a claim anyone should have to take on architecture alone — it's exactly what the 55-worker rejection analysis showed can't be assumed.

ADR-011 Open, scoped for Move 2

Evolve the verdict from a boolean into five gates

Today's VerificationResult.verdict is confirmed / rejected / unverified, one boolean-ish outcome per claim. The planned evolution, to be built alongside the Move 2 benchmark: CLAIM_VALID, EVIDENCE_VALID, ATTRIBUTION_VALID, DERIVATION_VALID, FRESHNESS_VALID, with VERIFIED defined as all required gates passing for that claim's shape.

Why open, not decided-and-built: two of the five gates already exist under different names — DERIVATION_VALID is exactly what ADR-009's computation check does today, and EVIDENCE_VALID is what quote_round_trips() checks today. But ATTRIBUTION_VALID has never actually been exercised: every worker in every scenario so far sees exactly one source document, so there is no current test case where a claim could be attributed to the wrong source, and FRESHNESS_VALID depends on Memory's TTL/supersedes design (ADR-007), which isn't built yet. Formalizing five gates now, with two of them untestable, would be documentation theater. Limitations also now records a related, confirmed-real gap: quote_round_trips() proves evidence is real, not that it entails the claim — exactly the boundary EVIDENCE_VALID vs. CLAIM_VALID is meant to draw.

ADR-013 Decided: measured

Move-1 result: crash-safety and arithmetic checks validated live; quote-discipline did not improve

Two live re-runs of the 55-worker scenario after ADR-009 landed. Full writeup: Move 1 re-validation. Run 1 crashed on a real KeyError (an operand missing its quote key), fixed and regression-tested; Run 2 completed clean, 5/5 fabrications caught. Raw rejection rate went up, 12.7% → 33.1%, but reading all 59 rejected/unverified claims individually against source: the crash-class bug is confirmed fixed on real traffic (4 live instances now fail closed instead of crashing), the new arithmetic check caught 2 unambiguous genuine numeric errors no quote-match or judge could have caught, and the rate increase is otherwise a new worker-side failure mode (the model misusing the computation field itself — null quotes, non-numeric operand values, a cluster of hallucinated pseudo-HTML "quotes" from one worker call) stacking on the still-unsolved quote-paraphrasing problem, not a drop in factual accuracy.

Why decided, not still open: the two things Move 1 existed to check — does the fix crash again under real traffic, does the new check catch real errors — both got direct, measured answers. A third thing (does the anti-echo prompt collapse the raw rejection rate) got a measured "no," which is itself a real result, not a blocker. A follow-up null-quote/value guard was also added the same session (same function, same failure class). Full suite: 51/51.

Why not iterate on worker prompting again right now: per ADR-010's sequencing, claim-level scoring buckets belong to Move 2's benchmark, not another ungated prompt tweak. Also confirmed: real claim count swung 229 → 194 → 151 across three runs of code that was identical for the last two — a single 55-worker run is not a stable rejection-rate estimate, which is why the worker-count sweep runs multiple repeats per source rather than one shot per scale point.

ADR-014 Decided: measured

Deterministic A/B confirms ADR-009's anti-echo fix works, at a real recall cost

A temperature=0 paired A/B (old vs. new worker prompt, same 5 sources, 10 calls total, run against a Colab-hosted GPU Ollama instance) isolates the ADR-009 prompt change from sampling noise. Full writeup: prompt A/B. Result: the schema-echo placeholder bug (10 of 29 rejections in the original analysis) reproduces deterministically under the old prompt on 2 of 5 sources and is completely absent from all 10 new-prompt claims — the cleanest confirmation yet that the specific fix works, because it's a controlled paired comparison rather than a noisy full-swarm re-run. Two costs surfaced alongside it: a genuine recall regression (the new prompt drops real, source-supported claims on 3 of 5 sources, not just re-wording them), and one concrete case of the computation field producing self-inconsistent arithmetic (recomputed 19 vs. claimed 34) on a claim that is almost certainly true — a false-rejection risk, not a caught error.

Why decided, not left open: the question this A/B was scoped to answer — is the quote-discipline problem sampling noise or a real prompt-driven effect — has a direct, measured answer for the specific echo bug (real, prompt-driven, fixed). The recall regression and the computation false-rejection risk are new, real findings, but per ADR-010's sequencing they are inputs to Move 2's benchmark (claim-level scoring buckets, false-rejection cost as a first-class metric per ADR-012) rather than another round of ungated prompt iteration now.

ADR-015 Decided: measured

N-worker sweep complete (1x–200x): two real crashes found and fixed, fail-closed holds at every scale

Question A from the Move-1 follow-up (does the swarm crash or break fail-closed as N scales, independent of rejection composition). Full writeup: N-worker scale sweep. N=1 and N=5 completed clean first try. N=20's first attempt crashed: a mid-run network read-timeout on one worker's extraction call raised an uncaught OllamaUnavailable that propagated out of the orchestrator and killed the entire 20-worker batch. Fixed with two independent changes — a code-level fix (OllamaSimWorker/Orchestrator now fail closed per-call on a transport error instead of crashing the batch, two regression tests added, 53/53 passing) and an infra-level one (the Colab notebook's ollama serve subprocess had its stdout pipe going nowhere, a plausible pipe-buffer deadlock once logging filled it; fixed by draining it on a background thread). With both in place, N=20 and N=100 both ran clean on the next attempt — at N=100's scale (375 real claims), fail-closed caught a much richer mix of malformed computation payloads and outright arithmetic mismatches than any smaller run had produced, without a single false confirmed. N=200 (2026-08-16, live remote dolphin3 via ngrok, not Colab-notebook-embedded) extended the sweep past its previous ceiling and found a second, different crash: a worker echoed the extraction prompt's own operand-schema description text ("verbatim source span this operand came from") as a dict key, wrapping a real quote as its value, and the whole malformed object landed in the claim's plain quote field instead of a string. _normalize() called .replace() on it directly and crashed the batch with AttributeError — never seen below N=200, a longer sweep surfacing a rarer shape, the same reason the N=20 network-timeout crash didn't appear at N=1–5 either. Fixed by making quote_round_trips() str()-coerce the quote before normalizing, the same defensive idiom computation_operands_round_trip() already used for this exact operand shape; one regression test added, full suite 54/54. The re-run then completed clean: 746 real claims, 5/5 fabrications caught, and the 3 live instances of the same dict-quote shape that appeared this time were correctly rejected, not crashed on. A claims-persistence write was also added to the sweep script immediately after extraction (before verification runs), so a future verification-phase crash can no longer silently discard the expensive extraction compute the way this one nearly did.

Why decided, not still open: the two things this sweep exists to check — does the swarm crash at higher N, does fail-closed hold under a wider failure mix at scale — both got direct, measured answers across the full 1x–200x range, and both real crashes found were fixed and regression-tested immediately, matching ADR-013's precedent for crash-class bugs rather than deferred to Move 2. Composition of rejections across N is explicitly out of scope here (that's the prompt A/B's job, run at fixed temperature on purpose) and not blocked on anything.

ADR-012 Decided

Milestone name: Groundswarm V0.2 — Verified Beats Plausible

Definition of done: on a fixed benchmark, Groundswarm demonstrates materially fewer unsupported claims than the identical unverified swarm, with measured false-rejection cost, compute overhead, and zero hidden verifier leakage reported alongside the win, not omitted.

Why name it now, before it's built: naming the finish line before Move 2 starts is what keeps Move 2 from quietly turning into "add more features" — the benchmark work only counts once this specific, falsifiable comparison exists and Groundswarm wins it cleanly. Until then this is "another agent framework with a verifier," not a research contribution.

ADR-016 Decided

Product pivot: open-source SDK/framework first, config/YAML-defined swarms, no UI for v1

Three scoped decisions, all user-confirmed: (1) product research runs now, with the Move-2 "Verified Beats Plausible" benchmark continuing as a parallel, non-gating workstream, not a prerequisite — both threads run at once, neither blocks the other. (2) target audience for v1 is the open-source SDK/framework crowd, not self-serve SaaS or an enterprise-sales-led motion. (3) the v1 surface for defining a swarm is config/YAML, not a no-code visual builder and not a code-only SDK — technical users, no UI. Grounded in two research passes: OSS packaging & monetization landscape (8 comparable frameworks, 8 open-core monetization cases, and a new combo-check finding: nothing found combines declarative swarm config with independent live-source verification, strengthening the differentiation case already made in the market survey) and YAML schema design precedent (docker-compose, GitHub Actions' permissions: block, dbt, Kubernetes/OPA Gatekeeper, six agent-orchestration export formats). The actual schema, my own design call grounded in that research rather than delegated to it, is on the swarm-schema page: sources/workers/verification as three unit types mapped 1:1 onto the existing WorkerTask/Orchestrator/Verifier code, fields marked real vs. reserved rather than overclaiming what's actually wired up, fail-closed at config-load time for an unresolved source reference — the same discipline the Verifier already applies at claim-check time.

Why parallel, not sequential: the user's explicit direction. ADR-010's original re-validate→benchmark→Memory sequencing gated later, riskier work (Memory) on an earlier result being proven; product research and schema design carry a different risk profile — they don't enlarge Groundswarm's own attack surface the way Memory would, so there's no equivalent reason to gate them on Move 2 landing first. The recommendation to build Move 2 first was made and heard; the user's call to run both at once stands.

Why declarative config, not a no-code builder or code-only SDK: the packaging landscape research found declarative config is a real, viable, non-novel choice in this space (swarms and CrewAI both ship it), and the combo-check finding means pairing it with independent verification is still an open, unclaimed position — not a bet made in the absence of precedent.

ADR-017 Decided: measured

Move-2 result: verification is the entire effect, at zero false-rejection cost

Two live runs of the 30-claim ground-truth benchmark (5 sources × 6 categories) against a remote dolphin3:latest, per ADR-012's design. Full writeup: Move 2 results; raw per-call cost: observability page. groundswarm caught 39 of 40 injected bad claims across both runs (97.5%) with zero false rejections of true claims; swarm_no_verification and single_agent — both reporting unconditionally, no Verifier call — leaked 40/40 in both runs, confirming the gap is attributable to the verification step itself, not to some upstream property of extraction. The one miss (run 1, an unverifiable claim wrongly confirmed by the LLM-judge fallback, correctly rejected on an identical re-run) is judge-path sampling variance, not a systemic hole — 0 false confirms on the deterministic quote/computation paths across both runs. Reading the real (non-injected) claims individually against source also surfaced two follow-on findings, neither of which this ADR closes: live instances of the EVIDENCE_VALID-vs-CLAIM_VALID gap already on record in Limitations (a real, round-tripping quote attached to free text asserting an unrelated, sometimes-wrong number), and a systematic omission pattern — negative/scope-limiting facts ("X was not affected," "no data was lost") are almost never extracted by any worker, in any run, in any of the three conditions.

Why decided, not still open: the two things Move 2 existed to check — does verification measurably beat unconditional reporting, and at what false-rejection cost — both got direct, measured answers on real (not simulated) model output, per ADR-012's explicit definition of done. The two follow-on findings are real but separately scoped: the EVIDENCE_VALID/CLAIM_VALID instances feed ADR-011 (still Open — this result gives it real test cases, it does not resolve it), and the omission pattern is a worker-prompting problem, not a verification one, tracked as a follow-up re-run rather than folded into this result.

Why wrong_attribution doesn't close ADR-011: all 5 wrong_attribution ground-truth claims were rejected cleanly, but through the existing EVIDENCE_VALID mechanism (the substituted quote genuinely isn't verbatim in that claim's declared source) — not through a dedicated attribution check. ADR-011's ATTRIBUTION_VALID gate is about a worker exposed to multiple sources misattributing a real quote between them; Move 2's workers, like every prior scenario, still see exactly one source each. That test case still doesn't exist.

ADR-018 Decided: built and measured

Supersedes ADR-001: Groundswarm merges with and manages OpenClaw's Gateway, not just calls into it

Cloning OpenClaw and reading its source directly (not just docs) showed ADR-001's original framing — "workers are OpenClaw instances" — doesn't fit OpenClaw's real architecture: a single always-on Gateway daemon, not a spawn-per-task binary. Per explicit user direction ("merge and get best of both, swarm manage the entire OpenClaw ops," then "symbiosis, a feedback-optimized loop"), the resolved design is: Groundswarm owns the Gateway's full lifecycle (ops/openclaw_manager.py: start, port-discover via the Gateway's own lock file, health-check, full-process-tree stop), and dispatches worker tasks through the Gateway's real agent-backed /v1/chat/completions endpoint (workers/openclaw_worker.py, implementing the same Worker protocol as OllamaSimWorker, one Gateway session per worker via a unique user field). A verification-outcome-driven feedback path back into OpenClaw's own routing is scoped in intent but not yet built. Full writeup, including the 404→500→root-cause debugging trail and the first live smoke-test result (3 real, source-grounded claims through a genuine agent turn): OpenClaw Gateway integration.

Why merge instead of the four narrower options considered (revise ADR-001 to a thinner HTTP-only integration, build the shallow path anyway, attempt a deep fork-and-modify integration, or drop OpenClaw entirely): the user explicitly rejected all four in favor of Groundswarm actively owning OpenClaw's operational lifecycle end to end. This is viable specifically because /v1/chat/completions was confirmed, by reading openai-http.ts in full, to already exercise a genuine OpenClaw agent run rather than being a bare model passthrough — the "shallow" HTTP path and the "deep" real-agent-capability path turned out to be the same endpoint, not a tradeoff to pick between.

Why decided-and-built, not left as an architecture note: the design was carried all the way through a real clone, a real build, a real running Gateway process managed entirely by new Groundswarm code, and a real end-to-end extraction call — including two genuine bugs found and fixed along the way (an implicit OpenAI-provider → Codex-harness routing default, and a silent Ollama model-discovery opt-in gate) rather than an integration that only works on paper.

ADR-019 Decided: built and measured

Feedback loop built and run live: same-session re-dispatch anchors the model on its first answer, fixed with a session per attempt

The verification-outcome feedback loop ADR-018 scoped in intent is now real code, run against the real Gateway: ops/feedback.py tallies a batch's VerificationResults per worker and generates a caution note once a worker's confirmed fraction drops below 80%; OpenClawWorker.source_notes injects it into that worker's next system prompt; a two-pass scenario runner dispatches all 5 real incident sources, verifies, flags the worst performer, and re-dispatches it. First full run: 27 claims, 18 confirmed / 9 rejected, cobalt_storage flagged at 0/4. The cautioned re-dispatch came back byte-for-byte identical to the original — a changed prompt producing zero change in output. Root cause, confirmed by reading the Gateway's own log rather than inferred: OpenClawWorker built its Gateway user key from worker_id alone, and user maps directly to a Gateway session (per ADR-018) — so both calls landed in one ongoing OpenClaw conversation, and the agent anchored on repeating its first turn rather than re-solving the task. A control test with a fresh session but the same caution note produced a measurably different result (2/4 confirmed, a different failure mode entirely), confirming session reuse, not prompt content, was what the null result was actually holding fixed. Fix: OpenClawWorker now folds a per-worker_id attempt counter into the Gateway user key, so a re-dispatch of the same worker identity lands in a fresh session automatically. Full writeup, including the markdown-code-fence bug that separately caused a 0-claims-from-all-5-workers regression along the way: OpenClaw feedback loop.

Re-validated in situ through the actual product code path: cobalt_storage dispatched twice through one live worker instance, pass 2 carrying the real caution note the pipeline generated. Pass 1: 0/4 confirmed, all rejected as invented paraphrase quotes. Pass 2: 3/3 confirmed, every claim left quote null instead of fabricating one — exactly what the caution note asked for — and the raw response was no longer identical to pass 1.

Why decided, not overclaimed: the anchoring bug and its fix are established by direct evidence (byte-for-byte log comparison, a fresh-session control test, an in-product re-validation), not by a plausible story. What is not yet established: whether the caution note's specific wording is what improved pass 2, versus a fresh, uncautioned re-roll landing on better output by chance — pass 2 is confounded on both variables at once (n=1, cautioned and freshly-sampled together). Isolating that needs a controlled fresh-session A/B, WITH vs. WITHOUT the note, repeated — the same discipline ADR-014 already applied to the anti-echo prompt fix. Explicitly scoped as follow-up, not claimed here.

ADR-020 Decided: built and measured

Add CLI-backed worker execution: route extraction through a real Codex CLI or Claude Code CLI subprocess, not just local Ollama

OpenClaw already supports routing its agent execution through a real Codex CLI or Claude Code CLI subprocess as config-only harness switches (plugins.entries.codex.enabled + an openai/<model> ref for Codex; a plain claude-cli/<model> model ref for Claude, which needs no OpenClaw-side secret at all since it reads the host's own claude auth login credentials directly). Three new modules (runtime_config.py, ops/openclaw_config.py, workers/factory.py) give Groundswarm a single construction point that mutates OpenClaw's own config (via its first-party config patch --stdin CLI, never a hand-rolled deep-merge) before starting the Gateway. Full writeup: CLI harness calibration.

Why: the user wanted a way to get faster/higher-quality extraction than the 6GB laptop RTX 3060 using credits/subscriptions already available on this host, without Groundswarm building its own second agent runtime — OpenClaw already had the capability, just not wired up. Both Codex and Claude Code are supported, and Groundswarm deliberately owns writing the OpenClaw-side config itself (not a manual runbook step), an accepted, understood increase in blast radius: this tooling now mutates a separate application's config, guarded by a stopped-Gateway precondition and a dry-run-before-apply check on every call.

Why decided-and-built, not left as a design note: both harnesses were verified against real backends, not simulated — claude_cli: 5 workers, 64 claims, 100% confirmed, 197,652 tokens/256.5s; codex under real ChatGPT-subscription auth (no API key at all): 5 workers, 45 claims, 100% confirmed, 135,112 tokens/91.6s. Getting there surfaced two real bugs no design review would have caught: both timeout defaults were tuned for a fast path and too tight for the model-catalog lookup a first-time harness switch actually performs (measured 210s and 478.8s against original 180s/300s caps, now 300s/600s), and the codex API-key SecretRef was written unconditionally even under subscription auth, which OpenClaw's own dry-run then eagerly resolved and rejected outright — fixed with an explicit openai_auth_mode: "subscription" option rather than papering over it.
