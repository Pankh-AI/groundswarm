Swarm Definition Schema (v1)

Product surface decision · 2026-08-15 · my own design call, grounded in schema precedent research and packaging landscape research, not delegated to either research pass
Per the user's confirmed direction: config/YAML-based, no UI for v1, technical users first. This page defines the actual YAML shape a Groundswarm user writes to declare a swarm — three unit types (sources, workers, verification), matching the three real components that already exist in code (WorkerTask/Claim, the Orchestrator, the Verifier) rather than inventing capability the codebase doesn't have yet. Fields are marked real where they map directly onto existing, tested code paths, and reserved where the field is defined now for forward compatibility but not yet enforced — stated explicitly rather than left ambiguous, consistent with this project's existing no-inflated-claims discipline.

The schema

groundswarm: 1                        # schema generation, dbt-style (not semver) -- bump only on a breaking field-shape change

swarm:
  name: incident-monitoring-demo
  instruction: "Extract the key findings from this incident postmortem."  # default WorkerTask.instruction for every worker below

sources:                               # named once, referenced by workers -- Compose-style reference-by-name,
  anchor_cdn:                          # not a path repeated inline at every worker that touches it
    type: file                         # only implemented value today -- see caveats
    path: ./sources/anchor_cdn_postmortem.txt
  cobalt_storage:
    type: file
    path: ./sources/cobalt_storage_postmortem.txt

workers:                               # a list, not a map: worker_id can repeat a source (the N-worker sweep's
  - id: anchor_cdn_w1                  # "_r2" repeat-worker pattern needs list semantics, a map key can't repeat)
    source: anchor_cdn                 # must resolve to a key under sources: -- unresolved reference is a load-time error, see below
    # instruction: ...                 # optional per-worker override of swarm.instruction

  - id: cobalt_storage_w1
    source: cobalt_storage

verification:
  quote_match: enabled                 # deterministic; cannot be disabled -- listed for visibility, not control
  arithmetic: enabled                  # deterministic; cannot be disabled -- listed for visibility, not control
  llm_judge:
    enabled: true                      # RESERVED: toggle defined here, Verifier doesn't read it yet -- see caveats
    model: dolphin3:latest

runtime:
  ollama_host: ${OLLAMA_HOST}          # Compose-style ${VAR} interpolation, not a code edit
  model: dolphin3:latest

Field-by-field: real vs. reserved

Field Status Maps to
sources.*.path, workers[].source, workers[].id real WorkerTask.source_path / .worker_id directly
swarm.instruction, per-worker override real WorkerTask.instruction — today hardcoded identically in every scenario script
runtime.ollama_host, runtime.model real OllamaClient(host=, model=) constructor args, already env-var-driven today
verification.quote_match, .arithmetic reserved always-on in Verifier.verify_claim(); schema field is documentation, no code reads it, and per fail-closed philosophy it never will be a real off-switch
verification.llm_judge.enabled reserved would let a swarm author route any claim with neither quote nor computation straight to unverified instead of the LLM fallback -- a real, small, buildable change to Verifier._judge()'s call site, not yet made
sources.*.type other than file reserved WorkerTask.source_path's own docstring: "a local fixture standing in for a live primary source during simulation" -- no live-fetch source type exists in code yet, type: file is the only value the (not-yet-written) loader would accept
None of this schema is parsed by any code yet either — the loader that turns this YAML into WorkerTask/Orchestrator/Verifier wiring is the concrete next engineering step this page sets up, not something this page claims already exists.

Design rationale

Three unit types, not one flat list. Sources, workers, and verification are three genuinely different kinds of thing with different lifecycles: a source is a reference to data that may be reused by multiple workers; a worker is one extraction task bound to exactly one source; verification is a policy that applies to the claims workers produce, not to the workers themselves. Collapsing them into one flat list (the way a lot of no-code tools do) would force verification config to live duplicated on every worker instead of declared once.

Why reference-by-name (Compose), not an explicit dependency graph (GitHub Actions' needs:)

Groundswarm's actual data flow has no case today where one worker's output feeds another worker's config at parse time — each worker reads exactly one source and reports claims; synthesis reads every worker's claims, a pure fan-in, not a general DAG. GitHub's needs:/ outputs: machinery solves a problem (arbitrary step-to-step data piping) Groundswarm doesn't have yet. If a real inter-worker dependency need shows up later, add it then — not speculatively now.

Why verification is attached where it's declared (dbt), not one global permissions-style block (GitHub)

GitHub's permissions: block is right for what it governs: ambient, workflow-wide defaults that every step inherits unless overridden. Groundswarm's verification methods aren't ambient defaults, they're mandatory, per-claim checks that already run unconditionally on every claim regardless of config — there's no scope in this codebase where "unlisted claim gets verified with a weaker default" is even a coherent state, because Verifier.verify_claim() has no notion of a claim with no applicable check (computation-or-quote-or-judge is a total function over every claim shape). The schema field that resembles GitHub's toggle (llm_judge.enabled) is scoped narrowly to which fallback path gets tried, never whether a claim gets checked at all.

What the "unlisted permission" question actually resolves to here

The precedent research flagged GitHub's all-or-nothing default-fill as a design question with no clean answer transferring in. Restated for this schema, the equivalent case is a config-load-time one, not a per-claim one: a worker whose source: doesn't resolve to any key under sources:. Consistent with the rest of this codebase's fail-closed doctrine (a malformed computation payload becomes unverified, never a guess), an unresolved source reference must be a hard validation error that refuses to run the swarm at all — not a silently-skipped worker and not a claim that quietly reports without a source. Fail closed at config load, the same way the Verifier already fails closed at claim-check time.

Why no version:/apiVersion: per-file field, but a top-level groundswarm: 1

Compose's answer (no version discriminator, unknown fields warn and are ignored) is right for a mature, slowly-evolving spec with a large installed base of existing files a change can't break. Groundswarm v1 has neither yet. dbt's per-resource version: 2 is closer to right for an early, evolving schema: a single integer that bumps only when a field's shape changes in a way old files can't be auto-migrated from, giving the (not-yet-written) loader a clean way to say "this file predates a breaking change" without a semver negotiation.

What was deliberately left out of v1

  • Memory. ADR-007 scoped Memory as a fourth architectural component, but it isn't built yet (see decisions). Designing a schema for a subsystem that doesn't exist is exactly the kind of speculative-future-requirement design this project's own operating discipline avoids; a Memory schema block gets designed when Memory gets built, not before.
  • A no-code visual builder. Explicitly ruled out by the user's own direction for v1 — technical users, config/YAML-based, no UI.
  • CrewAI's decorator-driven Python glue. CrewAI's YAML pair still needs a @CrewBase-decorated Python entry point to actually run (see packaging landscape). Groundswarm's target, closer to swarms' run-agents --yaml-file, is a YAML file plus one CLI invocation with zero required Python from the user — the loader is the only new code this implies, not a new authoring layer on top of the YAML.
  • A Gatekeeper-style two-file template/instance split for verification rules. Right shape for a large, open-ended set of rule types; overkill for the exactly-three, fixed-in-code rule types Groundswarm has today. Worth revisiting only if/when verification rule types become genuinely pluggable.
