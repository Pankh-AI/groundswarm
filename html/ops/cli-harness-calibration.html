CLI-backed worker execution — Codex/Claude Code harnesses, calibrated live

ADR-020's supporting record: routing worker extraction through a real Codex CLI or Claude Code CLI subprocess (via OpenClaw's own harness config) instead of the 6GB laptop Ollama GPU, plus two real config-mutation bugs live calibration found and fixed.
Result: both harnesses work end to end against real backends, no simulation. claude_cli: 5 workers, 64 claims, 100% confirmed, 197,652 tokens, 256.5s. codex (ChatGPT-subscription auth, no API key): 5 workers, 45 claims, 100% confirmed, 135,112 tokens, 91.6s. Getting there surfaced and fixed two real bugs in the config-mutation layer itself, not just in the harness code — both are documented below rather than smoothed into "it just worked."

What was built

ModuleOwns
ops/openclaw_config.pyapply_harness(): a thin, idempotent wrapper around OpenClaw's own config patch --stdin [--dry-run] [--json] CLI — validates, then applies, never hand-rolls the deep-merge/backup logic OpenClaw's CLI already owns (file locking, atomic writes, 5-deep backup rotation). Reads openclaw.json directly to skip the subprocess entirely when the requested harness already matches (no-op, no call). Never writes a plaintext secret: the codex harness's API key is stored as an OpenClaw SecretRef ({"source":"env","provider":"default","id":openai_api_key_env}), resolved by OpenClaw itself from an environment variable Groundswarm's own process already forwards to the Gateway subprocess.
runtime_config.pyRuntimeConfig: stdlib-only backend/harness selection (worker_backend: ollama|openclaw; openclaw_harness: direct|codex|claude_cli), env-var fallback at construction time, plus a generic harness_options passthrough bag so a future harness never needs a change here.
workers/factory.pyworker_session(): the single construction point. For openclaw it calls apply_harness() unconditionally, including for "direct" — the harness-switching bugfix baked into the design from the start: a gated call would let a Gateway a prior run left on codex/claude_cli silently stay that way forever the next time someone asks for "direct."

Migrated: scenarios/incident_monitoring_swarm/run_scenario_openclaw.py now builds a RuntimeConfig from env instead of hand-constructing OpenClawGatewayManager/OpenClawWorker directly, making GROUNDSWARM_OPENCLAW_HARNESS=codex / =claude_cli the real entry point. 54 new tests (test_openclaw_config.py, test_runtime_config.py, test_worker_factory.py); full suite 74/74.

Two real bugs, found only because calibration was run live

  1. Both timeout defaults were too tight for a real model-catalog lookup. apply_harness()'s dry-run/apply round trip measured 210s against a 180s cap for claude_cli; OpenClawGatewayManager's startup probe (which waits for the second "[gateway] ready" log line — full plugin+channel init, not the bare HTTP listener the first line signals) measured ~206s against a 300s cap. Both bumped (180s→300s, 300s→600s). The next live attempt against codex then hit the new 300s cap anyway — a first-time catalog validation of an unfamiliar openai/<model> ref under a real subscription account took 478.8s, confirmed directly in the dry-run call's own elapsed time. apply_harness()'s timeout_s default is now 600s.
  2. The API-key SecretRef was written even when nothing needed it, and OpenClaw's own dry-run eagerly resolves every SecretRef it's given. A subscription-authenticated codex CLI (codex login with a ChatGPT account, no OPENAI_API_KEY anywhere in the environment) got the whole patch rejected outright — "Environment variable OPENAI_API_KEY is missing or empty" — even though nothing about running codex through that CLI needs the variable. Root cause confirmed live, not guessed: _patch_for("codex", ...) unconditionally included the apiKey SecretRef, and config patch --dry-run resolves every SecretRef it's handed before validating anything else. Fix: a new openai_auth_mode: "api-key" | "subscription" parameter; "subscription" skips the apiKey patch entirely, relying on OpenClaw's own auth-requirement matrix already accepting a bare "chatgpt" account whenever authRequirement is left unset (which this patch never sets).

What's still open

  • Not yet measured: whether either CLI harness is actually faster/better than local Ollama for this workload. Both harnesses are proven to work and their own cost is measured (above), but the comparison that was the actual point of building this — CLI-backed vs. the 6GB laptop GPU, on the same source set — hasn't been run side by side yet.
  • Orchestrator.synth_client stays Ollama-only regardless of worker backend, so routing extraction through codex/claude_cli upgrades claim extraction only; briefing synthesis is still produced by the weakest model in the pipeline. Flagged as a real gap in the original design, not fixed here — see the plan's Phase 2 roadmap.
  • No concurrency ownership around the shared ~/.openclaw-dev state dir: apply_harness() guards against mutating a running Gateway, but not against two concurrent Groundswarm sessions racing different harness requests against the same profile. Fine for single-session use, a real gap otherwise.
  • Migrating Claude-CLI credentials into the separate mainline anthropic provider profile is explicitly out of scope — its only non-interactive route has no --dry-run and unverified safety against an already-onboarded profile.
