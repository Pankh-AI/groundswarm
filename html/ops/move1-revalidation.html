Move 1 — re-validating the ADR-009 fix against a live re-run

ADR-010's Move 1: don't claim the fix worked without measuring it. This page is that measurement — two live re-runs of the same 55-worker scenario, after the code changed, compared directly against the archived pre-fix run in rejection-analysis.html.
The honest headline: the crash-safety fix and the new arithmetic-recomputation check both validated on real production traffic, including catching the exact crash-class bug live. But the raw rejection rate did not go down — it went up, from 12.7% to 33.1%. That is not the fix failing; every rejection was read individually against source, and the increase is almost entirely a new worker-side failure mode (the model misusing the new computation field) stacking on top of the pre-existing, still-unsolved quote-paraphrasing problem — not new evidence that the swarm's underlying facts got less accurate.

What happened, in order

Run 1 (bykp22xko) — crashed after 5 workers' worth of extraction, with a live KeyError: 'quote': dolphin3 started using the new computation field (proof the ADR-009 prompt fix landed) but emitted at least one operand missing its "quote" key entirely, which computation_operands_round_trip() accessed unguarded. Fixed by moving that access inside the same try/except (KeyError, TypeError) that already caught malformed operation/operands/result keys, plus two regression tests reproducing the exact shape. Full suite green (49/49) before re-running.

Run 2 (bdgfa2fet) — completed clean, exit 0, all 5/5 fabrications caught. This page's numbers are from this run.

Follow-up fix, same session — reading Run 2's output surfaced a second, smaller gap in the same function: an operand with JSON null for quote or value (present key, empty content) doesn't raise KeyError, so it fell through to str(None) → the literal text "None", producing a misleading rejection reason ("quote does not appear in the source") when the real problem was that the worker provided nothing at all. Now checked explicitly with a clear reason; two regression tests added. Full suite green (51/51).

1. What actually validated — the crash fix, confirmed on live traffic

Of the 9 unverified/fail_closed claims in this run, 4 are the exact crash-class bug from Run 1 (meridian_cache_r1, meridian_cache_r4, meridian_cache_r9, solace_queue_r6: computation payload malformed: 'quote') — a missing operand key that used to kill the entire run now correctly resolves to one claim failing closed. This is not a hypothetical regression test passing; it's the same failure shape happening again in real dolphin3 output and being handled correctly the second time. A 5th (anchor_cdn_r5, missing 'result') is the same family. The remaining 4 are new-but-related shapes (an operation literally named "none" with zero operands, a sum over a non-numeric operand, a one-operand duration_minutes) — all correctly refused rather than guessed at. Zero crashes, zero silent passes, across all 9.

2. What actually validated — the computation check catching real arithmetic errors

Of the 14 computation-method rejections, 2 are unambiguous, exactly the class of bug ADR-009 exists to catch:
anchor_cdn_r4: recomputed duration_minutes = 28, but claim asserted 34 ridgeline_auth_r7: "errors starting at 20:02 UTC until it was resolved at 20:14 UTC, a duration of 22 minutes" — recomputed = 12
Neither of these has any quote-formatting problem — the operands round-tripped into source just fine. The number itself was wrong, and only independent recomputation (not a quote match, not an LLM judge re-deriving the same arithmetic) could have caught it. This is the direct, positive result: the third verification method is pulling its weight on real model output, not just on the hand-built test fixtures.

3. What did not validate — the anti-echo prompt fix, and a new failure surface

The other 12 of 14 computation rejections and the great majority of the 36 deterministic rejections are not genuine content errors. Reading all 50 individually against source:
  • ~10 of 14 computation rejections are the worker misusing the new field itself: attaching a computation object to a claim that isn't actually a derived number (e.g. a claim about a mitigation plan, or "no data was lost"), with operand value fields like "..." or a full clause instead of a number, or a quote that's an empty string. Two more (solace_queue_r7: recomputed 1432 vs claimed 8; cobalt_storage_r11: recomputed 104 vs claimed 1) have implausibly large deltas that look like the worker picked the wrong two timestamps/numbers to feed the operation, not that the claim text itself is false.
  • ~30+ of 36 deterministic rejections are the same paraphrase/non-verbatim-quote pattern already documented in rejection-analysis.html — the model still doesn't reliably copy the source verbatim into quote even with the anti-echo instruction in place. The placeholder-echo failure mode specifically (the literal schema description text) appears gone from this sample; paraphrasing is not.
  • New this run: a single worker call, cobalt_storage_r1, produced 5 quotes that look like hallucinated HTML/CSS fragments — e.g. <span class="highlight/degraded-disk\';>> failed hardware — text that never existed in the source at all, not a paraphrase or truncation of something real. One anchor_cdn_r8 quote came back as the literal string <PRESIDIO_ANONYMIZED_PERSON> automation, expired API token. Both are the model generating garbage in the quote field for that specific call, correctly rejected, but a failure mode not seen in the pre-fix baseline.
Net read: the crash-safety and arithmetic fixes are real, validated wins. The prompt-level fix for quote discipline is not yet working, and the new computation field gave the model a second field to be undisciplined in, which is why the raw rejection rate went up rather than down. This is squarely a worker prompt-engineering problem, not a verifier defect — consistent with every rejection-analysis finding so far: the verifier has not yet let a single fabrication or a single confidently-wrong number through, in either run.

Methodological caveat: single-run point estimates aren't stable

Real claim count moved 229 → 194 (Run 1, crashed) → 151 (Run 2) across three runs of what is, for the last two, identical code — a ~22% swing between two back-to-back runs with nothing but dolphin3's own sampling variance as the difference. A single 55-worker run's raw rejection rate is therefore not a stable estimate of anything; it should be read as one sample, not a verdict. This is exactly why the worker-count sweep below is designed to run multiple repeats per source rather than one run per scale point — and why Move 2's benchmark (ADR-010) will need repeated trials, not single-shot comparisons, to say anything the small-n data here can't already contradict on the next run.

What's next

Per ADR-010, the worker-count sweep (N=1/5/20/100, same fabrications, same base sources) runs next — primarily to check that crash-safety and fail-closed behavior hold as call volume scales, and secondarily to get a first read on whether rejection-rate composition (paraphrase vs. computation-misuse vs. genuine error) shifts with scale. It is explicitly not expected to produce a stable point-estimate of "the" rejection rate, per the caveat above. The quote-discipline prompt problem is left open rather than iterated on again immediately — per ADR-010's sequencing, Move 2 (the benchmark) is where claim-level scoring buckets (supported / unsupported / unverifiable / wrong computation) get formalized, and that's the more useful place to fix worker prompting against a fixed, scored target instead of one more ungated iteration.
