OpenClaw Gateway integration — manager, worker, and the first live smoke test

ADR-018's supporting record: the real architecture found by cloning and reading OpenClaw's own source, the merged design that resulted, and the debugging trail from a 404 all the way to a working extraction call.
Result: it works. A real OpenClaw Gateway process, started and stopped entirely by Groundswarm's own code, ran a genuine agent turn against a local Ollama model and returned three correctly-quoted claims from a real source document over the same Worker protocol OllamaSimWorker already implements. Two real bugs stood between "the Gateway starts" and that result, both root-caused to specific lines of OpenClaw source rather than guessed at, and both are recorded below so the fix isn't mistaken for a workaround.

What OpenClaw's architecture actually is

Not a stateless per-call worker process — a single always-on Gateway daemon (node scripts/run-node.mjs --dev gateway) multiplexing WebSocket control/RPC and HTTP on one port, discoverable only via a lock file it writes at <state_dir>/tmp/openclaw/gateway.<hash>.lock (JSON: pid, port, startTime, ...) — there is no fixed default port in source. This is why the original ADR-001 framing (OpenClaw instances as the worker runtime, one per worker) doesn't fit: OpenClaw is one persistent operator process, not a spawn-per-task binary.

Its /v1/chat/completions endpoint is not a bare completions passthrough. Reading src/gateway/openai-http.ts (1502 lines) in full: handleOpenAiHttpRequest translates the request into a genuine agentCommandFromIngress() agent run — the agent's configured tools, session and memory all apply — and wraps the agent's final text back into OpenAI chat-completion JSON. Passing a unique user field per request (sessionPrefix: "openai") gives each call its own Gateway session, which is what keeps this compatible with N independent parallel Groundswarm workers instead of accidentally threading them through one shared OpenClaw conversation.

The merged design (ADR-018)

Per the user's direction — merge, don't pick a side; Groundswarm manages OpenClaw's entire ops — two new modules:
ModuleOwns
ops/openclaw_manager.pyOpenClawGatewayManager: starts the Gateway subprocess, discovers its dynamically-assigned port by polling for a fresh lock file, health-checks it over HTTP, and tears down the full process tree on stop (taskkill /PID <lock-file pid> /T /F on Windows — the lock file's PID, not just the immediate Popen child, because dev-mode startup spawns rolldown/tsdown child processes for plugin bundling). Context-manager support (__enter__/__exit__).
workers/openclaw_worker.pyOpenClawWorker, the same Worker protocol OllamaSimWorker implements (run(WorkerTask) -> WorkerOutput), calling the Gateway's real agent-backed /v1/chat/completions instead of Ollama directly. Same fail-closed idiom on transport failure: a Gateway that's unreachable degrades to zero claims, it does not crash the batch.

Both are stdlib-only (subprocess, urllib.request, json, pathlib), matching ollama_client.py's existing dependency policy (pyproject.toml: dependencies = []).

Feedback loop: scoped in intent, not yet built. The user's framing was explicit — "symbiosis, a feedback-optimized loop," not a one-way dispatch pipe. The verification signal Groundswarm already produces per claim (confirm/reject/fail-closed rate, per-source and per-worker reliability) is the natural input; how it should feed back into OpenClaw's own routing/prioritization is deliberately left open here rather than designed speculatively ahead of the base integration being proven. Tracked as follow-on work, not silently dropped.

Debugging trail: 404 → 500 → root cause → 0 claims → 3 real claims

  1. 404 on /v1/chat/completions. Traced through server-runtime-config.ts: openAiChatCompletionsEnabled defaults false. Fix: config set gateway.http.endpoints.chatCompletions.enabled true.
  2. 500, "Agent harness runtime "codex" is unavailable because its plugin registration is missing." Root cause, found by reading src/agents/harness/policy.ts and src/agents/openai-routing.ts: any openai/*-provider model implicitly routes agent execution through the real Codex CLI harness (resolveOpenAIImplicitAgentRuntime) unless an explicit agentRuntime policy overrides it — by design, the same way Anthropic models route through the Claude Code CLI. This dev build has no Codex plugin registered, so every openai/gpt-* call failed. An earlier attempt to fix this via agents.entries.dev.runtime.type = "embedded" was the wrong config key entirely (a different type, AgentRuntimeConfig, than the one this resolution path reads, AgentRuntimePolicyConfig) and had no effect. The actual fix was routing the agent to a non-OpenAI provider, which skips this code path outright (isOpenAIProvider() gates it).
  3. Ollama models invisible to models list despite enabling the plugin. Traced into extensions/ollama/src/discovery-shared.ts: discovery requires an explicit opt-in (a non-empty apiKey string on models.providers.ollama) or meaningful explicit provider config; plugins.entries.ollama.enabled and ...config.discovery.enabled alone satisfy neither gate and silently no-op. Fix: config set models.providers.ollama.apiKey "local-dev" (any placeholder string), then config set agents.entries.dev.model "ollama/dolphin3:latest", which validated clean.
  4. Call succeeded (200, real tokens) but parsed 0 claims. completion_tokens=72 on a multi-fact extraction task is a truncation signature, confirmed by the raw response being valid-looking but unclosed JSON. Root cause: OpenClawWorker never set max_tokens in the request payload, silently relying on an undocumented server-side default — the same omission OllamaSimWorker has, just never surfaced because direct Ollama calls in this codebase are shorter. Fix: added an explicit max_tokens: int = 1024 field, set on every request.
  5. Clean run. 3 claims, each with a quote that round-trips into the source document, from a real local model via a real OpenClaw agent turn.

Live smoke test result

smoke_openclaw_worker.py: manager starts the Gateway → OpenClawWorker.run() against anchor_cdn_postmortem.txt → manager stops the Gateway. Full cold run (build + Gateway start + agent turn) completes in well under the manager's 300s startup budget; the agent call itself took 30.0s, 4,926 prompt tokens, 134 completion tokens.

What's still open

  • The feedback loop itself (verification outcome → OpenClaw routing/prioritization) is designed-in-intent only, per ADR-018 above — no code yet.
  • This was validated with one dev agent, one local model, one source file, one call. Not yet run through the N-worker sweep harness or the Move-2 benchmark that gate the rest of Groundswarm's claims.
  • OpenClawGatewayManager's process-tree teardown is Windows-specific (taskkill /T /F); untested on Linux/macOS.
