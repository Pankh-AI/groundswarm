N-worker scale & crash-safety sweep

Question A from the Move-1 re-validation follow-up: does the swarm crash, corrupt state, or violate fail-closed behavior as N scales — independent of rejection-rate composition, which is Question B, answered separately by the prompt A/B. Run via run_scenario_sweep.py at N=1, 5, 20, 100 against a Colab-hosted GPU Ollama instance (see infra note), and at N=200 against a separate live remote dolphin3 instance (ngrok-tunneled, not Colab-notebook-embedded — see Move 2's infra note).
All five scale points now run clean, zero crashes — but two of the five first attempts did crash, each on a genuine bug this sweep exists to catch. N=20: a mid-run network read-timeout on one worker's call raised an uncaught exception that propagated out of the orchestrator and killed the entire 20-worker batch, discarding every other worker's completed work. N=200: a worker echoed part of the extraction prompt's own schema-description text as a dict key and wrapped a real quote inside it, landing a JSON object where the verifier expected a plain string; _normalize() crashed calling .replace() on it directly. Each was fixed the same way — live, on real traffic, regression-tested before moving on, never patched around instead of understood — and neither has recurred on any re-run since. At N=100 and N=200, the verifier's fail-closed logic held under a much richer mix of malformed and inconsistent claims than any smaller run had produced, without a single false confirmed.

1. Zero crashes across all four scale points, after fixing one real crash

N=1 and N=5 never crashed. N=20's first attempt did (see finding 2); after the fix, N=20 and N=100 both ran to completion cleanly, each producing a well-formed verification log, Memory writes, and an observability report. This is the same class of check Move 1 already exercised once against a real 55-worker run (a genuine KeyError found and fixed there); this sweep found a second, different crash class at higher worker count and fixed it the same way — live, on real traffic, regression-tested before moving on — rather than treating a blocked run as an acceptable stopping point.

2. The crash that broke N=20's first attempt, and two independent fixes

The first N=20 attempt failed with an uncaught exception, not a graceful rejection:
groundswarm.llm.ollama_client.OllamaUnavailable: could not reach Ollama at https://ability-cartoons-sacred-relative.trycloudflare.com: The read operation timed out
raised from inside OllamaClient.generate() during one worker's extraction call, and never caught anywhere above it — it propagated straight out of Orchestrator.run()'s worker loop and killed the whole batch. Unlike a null quote or an unparseable computation, which the Verifier already turns into a graceful unverified, a transport-level failure on the extraction call itself had no such handling. At N=1 or N=5 the odds of any single call hitting a transient network hiccup are low; at N=20, four times the sequential Ollama calls means four times the exposure window, and one did.

Fix 1 (code, this repo): OllamaSimWorker.run() now catches OllamaUnavailable around its extraction call and degrades that one worker to zero claims, the same treatment already given to an unparseable response, instead of letting the exception escape. Orchestrator.run() got the matching guard around the synthesis call, so a failed briefing no longer discards the extraction workers' already-verified claims. Two regression tests added (test_sim_worker.py, plus a new case in test_orchestrator.py); full suite 53/53.

Fix 2 (infra, Colab notebook, not this repo): the notebook's ollama serve cell launches the process with stdout=subprocess.PIPE but nothing ever read from that pipe. Once the server's own logging fills the OS pipe buffer, the write blocks and the process can stop servicing requests entirely — a plausible root cause for the read timeout above, not just a coincidence. Fixed by draining ollama_proc.stdout in a background thread; confirmed directly by inspecting the live notebook's cells before trusting the diagnosis, not taken on faith. This fix lives in the ephemeral Colab session, not in version control, so it needs to be re-applied on any future rebuild of that notebook.

3. Fail-closed held under a much richer failure mix at N=100

At 100 workers, the verifier's fail-closed paths caught a genuinely wider variety of malformed and self-inconsistent claims than any smaller run surfaced — unsupported computation operations ("none", "text"), operands with no quote at all, operand text that doesn't appear in its own cited span, and six separate cases where the recomputed arithmetic flatly disagreed with the claimed number (e.g. recomputed duration_minutes = 28, but claim asserts 34; recomputed difference = -78.0, but claim asserts 0.5). Every single one of these came back rejected or unverified, never confirmed — across 375 real claims and three independent verification methods, fail-closed did not slip once at this scale.

4. Malformed computation payloads: seen at every scale from N=5 up

First flagged at N=5 (two real claims with a computation object missing a required key), the same pattern recurs at N=20 and N=100 — missing quote/result keys, plus new variants (operation: "none" with empty operands, an operand whose value is itself the claim's prose rather than a timestamp). The verifier fails closed on all of them rather than guessing or crashing. Several of the underlying claims are very likely true — the durations they assert are directly statable from source timestamps — so, consistent with the prompt A/B's finding, this remains a false-rejection risk pattern worth a scored bucket in Move 2's benchmark, not a correctness bug in the verifier itself.

5. Caution (N=5 only): some fabrication catches were infra-driven, not judge-driven

Of the 5 injected fabrications at N=5, 3 were caught deterministically and 2 came back unverified because the LLM-judge fallback call itself timed out — correct fail-closed behavior, but it means that run's "5/5 fabrications caught" partly reflects infra flakiness under concurrent load rather than pure judge accuracy. At N=20 and N=100, all fabrication catches were genuine (no judge-timeout fail-closed among them), consistent with the pipe-deadlock fix removing the specific infra flakiness that caused N=5's judge timeouts.

6. The crash that broke N=200's first attempt: a new schema-echo variant

The first N=200 attempt extracted all 746 real claims successfully (the expensive, remote-LLM-call phase) and then crashed 20 calls into verification:
AttributeError: 'dict' object has no attribute 'replace' File "verifier\checks.py", line 19, in _normalize text = text.replace(curly, straight)
One worker (meridian_cache_r36) produced three claims whose quote field was a JSON object, not a string:
"quote": {"verbatim source span this operand came from": "The incident was detected by an automated staleness monitor at 03:22 UTC and the broker partition was manually rebalanced at 03:27 UTC. Full cache freshness was restored by 03:41 UTC."}
That key text is copied verbatim from the extraction prompt's own computation.operands[].quote schema description — the worker appears to have started drafting a computed claim, abandoned it, and left the operand-shaped fragment glued onto the plain quote field of a claim it ultimately expressed without a computation object. This is a new manifestation of the same schema-echo failure family ADR-009/ADR-014 already documented (the model echoing its own prompt's instructional text into output) — previously seen as a whole placeholder string standing in for quote, this time as a fragment used as a dict key wrapping real content, in a field position (quote, not computation.operands) the anti-echo prompt fix was never written to check. quote_round_trips() assumed claim.quote was already a string and called .replace() on it directly, unguarded — unlike computation_operands_round_trip(), which already str()-coerces its operand value/quote fields for exactly this reason. Fixed by applying the same coercion in quote_round_trips(); one regression test added (test_quote_round_trip_fails_closed_on_a_dict_quote), full suite 54/54. Also added: a persistence write for extracted claims immediately after extraction and before verification, so a future crash in this phase can't discard ~40 minutes of already-completed remote LLM calls the way this one nearly did — the crashed run's 750 extracted claims were unrecoverable (this persistence write didn't exist yet) and had to be re-extracted from scratch on the next attempt.

7. All three re-surfaced dict-quote claims were caught clean — and two are exactly the facts Move 2 found workers never extract

On the re-run, the same worker produced the identical malformed shape again for three claims (the str()-coercion makes this deterministic, not a sampling fluke): all three rejected ("quote does not appear in the source text, invented or altered"), zero crashes, zero false confirmed. Two of the three are notable for a different reason: they are near-exact matches for checklist items Move 2's omission finding reported as never extracted by any worker in either Move 2 run — "No customer data was exposed or corrupted" (meridian_cache's negative/scope-limiting fact) and "The incident had a total duration of 27 minutes" (meridian_cache's duration fact, and the same 27-minute figure Move 2's finding 4 already flagged as attempted-but-rejected on a different malformed-payload shape). This worker call did attempt both facts here — it just botched the output shape doing so. Consistent with Move 2's own read: the negative-fact gap looks like a worker-output-shape/prompting problem the model occasionally does attempt to close on its own, not a hard capability ceiling.

Caveats

None of these five runs used temperature=0, so confirm/reject/unverified counts across N are not a controlled comparison and should not be read as a scale-driven composition trend — per ADR-013, a single run at fixed code is already known to swing run-to-run from sampling alone. What this page answers is narrower and now complete: does the swarm crash or break fail-closed as N scales from 1 to 200 — no, not after the fixes above. Rejection-rate composition (quote-format vs. computation-misuse vs. genuine content error) remains the prompt A/B's job, isolated from both sampling and scale on purpose. N=200 also ran on different infra than N=1–100 (a separate ngrok-tunneled remote instance, not the Colab-notebook ollama serve cell the N=20 pipe-deadlock fix targeted) — it completed with zero pipe-deadlock-shaped failures, but that's one clean run on different infra, not confirmation the original fix generalizes; it simply didn't need to fire here.
