Move 2 — Verified Beats Plausible, measured

ADR-010/012's Move 2: a fixed, hand-authored 30-claim ground-truth corpus (5 sources × 6 categories) scored across three conditions — groundswarm (swarm + Verifier, only confirmed reported), swarm_no_verification (identical extraction, everything reported unconditionally, Verifier never called), single_agent (one call across all 5 sources concatenated, no decomposition, no verification) — run twice live against a remote dolphin3:latest (ngrok-tunneled Colab GPU). Raw numbers: observability page; full per-claim log: move2_benchmark_claims.json.
The honest headline: verification is the entire effect, not a marginal improvement. Both unverified conditions leaked 100% of injected bad claims, both runs (40/40 across run 1 + run 2 combined) — by construction, since neither ever checks anything, but that also confirms the ground-truth corpus's bad claims really do survive extraction and would reach a reader if nothing gated them. groundswarm caught 39 of 40 (97.5%) with zero false rejections of true claims across both runs. The one miss, and a live instance of a gap already on record in Limitations, are both reported below rather than folded into the headline number.

What happened, in order

Infra note: the original Colab/Cloudflare tunnel died mid-session (HTTP 530) and the colab-mcp browser bridge would not reconnect — an infra blocker, not a code one. Both runs below used a separately-launched Colab instance (ngrok, reserved domain, plain HTTP to OLLAMA_HOST) that never depended on the broken browser bridge at all.

Run 1 — swarm extracted 13 real claims. groundswarm leaked 1/20 bad claims (one unverifiable ground-truth claim was confirmed by the LLM-judge fallback instead of rejected). Exit code 1 — correct, designed behavior: main() returns non-zero exactly when not every bad claim was caught, the same convention run_scenario_sweep.py uses. Not a script bug; a real, substantive finding about judge-path reliability, reported honestly below rather than discarded and re-run until clean.

Run 2 — swarm extracted 20 real claims (same code, same corpus, sampling variance only). groundswarm leaked 0/20. Per-claim diagnostic logging (move2_benchmark_claims.json) was added between the two runs specifically to be able to read individual claims against source rather than trust the aggregate numbers alone — the analysis below is built from that log.

1. Verification is the entire effect, by construction and by measurement

swarm_no_verification reuses exactly the same extraction output as groundswarm — same workers, same claims, same sampling — and just reports everything unconditionally instead of routing it through the Verifier. It leaked 20/20 bad claims in both runs, every category, both times. single_agent, extracting independently with no decomposition, did the same. This isn't a weak-baseline artifact: it's confirmation that the 20 injected bad claims (unsupported, unverifiable, wrong_attribution, incorrect_computation) are genuinely present in what gets extracted and would reach a reader if nothing checked them — the corpus is doing its job, and the entire 39/40-vs-0/40 gap is attributable to the Verifier step, not to some upstream property of the extraction that quietly filters bad claims before verification even runs.

2. The one leak: judge-path variance, not a systemic hole

Run 1's single leak was an unverifiable ground-truth claim, confirmed instead of rejected. unverifiable claims have no quote or computation field by design (that's what makes them unverifiable) — they resolve entirely through the LLM-judge fallback, the one non-deterministic path in Verifier.verify_claim(). Run 2, identical code and corpus, ran this same claim through the judge again and it was correctly rejected. This is consistent with this project's own established finding (Move 1, ADR-013) that a single run is a sample, not a stable estimate — here it shows up specifically on the judge path, the one place in the verifier where that variance has anywhere to hide. It does not show up on the deterministic quote-match or computation paths in either run: 0 false confirms there, both times.

3. A live instance of the EVIDENCE_VALID vs. CLAIM_VALID gap

Limitations already documents, as a confirmed-real (not hypothetical) gap: quote_round_trips() proves a quote is genuine, not that it entails the claim's text. Move 2's real (non-injected) swarm claims produced three concrete instances of exactly this shape — a claim with a real, verbatim-matching quote attached, whose free-text asserts a number the quote doesn't actually establish and no computation field was populated to check:
anchor_cdn: "Manual intervention resolved the issue in 14 minutes" — quote covers 06:19–06:34 UTC verbatim (real), but the source's own timestamps put the fix at 15 minutes, not 14. CONFIRMED anyway. ridgeline_auth: "The batch job was running for 12 minutes before being killed" — quote is an unrelated alert timestamp (real), 12 minutes happens to be arithmetically correct. CONFIRMED — right number, but by luck, not by the mechanism that fired. ridgeline_auth: "Killing the job took 2 minutes" — quote is a real, unrelated sentence about pool recovery; the source gives no basis anywhere for "2 minutes." CONFIRMED anyway.
Two of these three are a genuinely wrong number sailing through as confirmed, not a near-miss — live, un-injected dolphin3 output reproducing a gap the project had previously only demonstrated with a hand-built example. This is exactly the boundary ADR-011's planned EVIDENCE_VALID vs. CLAIM_VALID gate split is meant to close; Move 2 gives it its first measured real-world instances rather than a constructed one.

4. The known quote-paraphrasing false-rejection pattern reproduces

Of run 2's 20 real swarm claims, 13 confirmed and 7 rejected. Reading all 7 individually against source: 3 are pure punctuation drift on true content — a comma the worker inserted or dropped, or a period added at a clause boundary the source doesn't actually break on (solace_queue's "backlog reached 340,000", solace_queue's "receiver identified at 12:03 UTC", ridgeline_auth's "3 minutes after identification" — the last of which is also a correct derived number, rejected purely on formatting). 1 is garbled phrasing that changes enough words to legitimately fail an exact match (solace_queue: "delivering order-event by" vs. the source's "delaying order-event delivery"). 2 are the worker fabricating or misconstructing evidence — ridgeline_auth's "22-minute incident window" synthesizes a timestamp ("20:24") that never appears in source; meridian_cache's "resolved in 27 minutes" pairs a genuine fact (the source does state a 27-minute total) with an altered, non-matching operand quote. 1 is a malformed computation payload (cobalt_storage: an operand missing its quote key entirely) — correctly unverified/fail_closed regardless of whether "51 minutes" is true. Same composition as Move 1: the rejection count is dominated by quote-fidelity friction on true claims, not by the verifier missing genuine content errors.

5. Omission is real and systematically asymmetric — not a heuristic artifact

groundswarm/swarm_no_verification missed 8 of 10 checklist items in both runs. Read against the raw claims log rather than trusted as a bare number: the 2 covered items in run 2 (anchor_cdn's and ridgeline_auth's duration facts) were genuinely present — the keywords showed up in real claims' combined text+quote. The 8 missed items split into two distinct failure shapes:
  • 6 of 8 are negative / scope-limiting facts — "only X was affected, other hostnames weren't," "no write requests were affected, no data was lost," "no customer data was exposed," "valid tokens were not logged out," "no messages were dropped." None of these appear in any real claim from any worker, in either run. This isn't a keyword-matching miss on a paraphrase — the workers simply never extracted an absence claim at all, in 5 sources and 2 independent runs.
  • 2 of 8 are duration numbers the worker either attempted and had rejected on a construction error (meridian_cache's 27-minute claim, finding 4 above) or never attempted a computation for at all (solace_queue's 8-minute detect-to-throttle gap).
The negative-fact gap is the more important one: it reproduces identically across both runs and hits all three conditions equally (A and B share extraction; single_agent misses 8/10 and 10/10 — never better). It is not something the Verifier can fix — it can only judge claims that exist, and no worker is producing "X was not affected" as a claim shape at all. The likely cause is that the extraction prompt asks "what happened," and absence-of-impact is exactly the kind of fact that framing doesn't surface. The closure direction is a prompting fix, not a verification one: an explicit "what was not affected / what did not happen" extraction pass or checklist, tested the same way the quote-discipline fix was — live re-run, not assumed.

Methodological caveats

Single/double-run point estimates aren't stable. Real claim count moved 13→20 and the leak count moved 1/20→0/20 between two runs of identical code and corpus — consistent with Move 1's already-established finding that dolphin3 sampling variance alone produces double-digit-percent swings. Both runs are reported above; neither is cherry-picked.

omission_rate() is a keyword heuristic, not semantic matching, and it checks coverage across all of a source's real claims combined, not whether any single claim states a fact coherently — e.g. ridgeline_auth's duration item counted "covered" because two separate claims' quotes jointly contained both timestamps, not because one claim stated the duration correctly. This makes the metric more generous than a stricter per-claim check would be, which is why the negative-fact gap (finding 5) is reported by reading the raw claims directly rather than trusting the aggregate number alone.

wrong_attribution claims are caught by the existing EVIDENCE_VALID mechanism, not a new one. All 5 rejected cleanly because the substituted quote genuinely isn't verbatim in that claim's declared source. This is not the same as exercising ADR-011's planned ATTRIBUTION_VALID gate, which requires a worker exposed to multiple sources that could genuinely misattribute a real quote between them — Move 2's workers, like every prior scenario, still see exactly one source each. ADR-011 stays Open; this result doesn't close it.

What's next

Per ADR-012's definition of done, Move 2 now has a measured result, not just a built-and-pending harness: verification is confirmed to be the entire effect (39/40 vs. 0/40), at zero false-rejection cost, for a compute overhead of roughly 2× single_agent's token count and comparable wall time. Two concrete, scoped follow-ups came out of reading the real claims individually rather than trusting the aggregate score: (1) the EVIDENCE_VALID/CLAIM_VALID gap (finding 3) now has real instances to design ADR-011's gate split against, instead of only the hand-built example in Limitations; (2) the negative-fact omission gap (finding 5) is a prompting problem worth a targeted fix and a re-run, independent of and not gated on the ADR-011 work.
