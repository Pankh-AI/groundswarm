OpenClaw feedback loop — built, and a same-session anchoring bug that defeated it

ADR-019's supporting record: the closed-loop pipeline actually running end to end through the real Gateway, the null result it first produced, the root cause traced live in the Gateway's own log rather than guessed at, the fix, and an honest read of what the fix does and doesn't yet prove.
Result: the loop runs end to end, and the first version of it didn't work — for a reason that took direct evidence to find. Groundswarm's own Verifier output now reshapes a flagged worker's next dispatch through the real OpenClaw agent, not a simulated one. The first attempt produced a null result: a corrected system prompt came back with the byte-for-byte identical answer. The cause was the Gateway's session semantics, not the prompt content — confirmed by reading the raw agent responses in the Gateway's own log, not inferred from the verifier's output alone. Fixed by giving each dispatch attempt its own Gateway session; the in-product re-run then showed a real, different response and a real swing in confirmed claims. What that swing is and isn't evidence of is stated plainly in the last section, not left to be assumed.

What was built

ModuleOwns
ops/feedback.pycompute_reliability() groups a batch of real VerificationResults by worker_id and tallies confirmed/rejected/unverified; SourceReliability.needs_caution fires once a worker's confirmed fraction drops below CAUTION_THRESHOLD = 0.8 (deliberately permissive — at single-digit per-worker sample sizes a stricter cut fires on noise as often as on a real problem); caution_note() renders a short instruction naming the observed rate, not a guessed cause, since the Verifier's per-claim rejection reasons aren't threaded through here.
workers/openclaw_worker.pyOpenClawWorker.source_notes: a per-worker_id caution string, appended to that worker's system prompt on its next dispatch if present. Writing into this dict is the entire mechanism — nothing else about OpenClaw's config, channel routing, or model choice is touched from Groundswarm.
scenarios/incident_monitoring_swarm/run_scenario_openclaw.pyTwo-pass live runner: dispatch all 5 real incident sources through OpenClawWorker → Orchestrator synthesis → Verifier on every claim → compute_reliability() → the worst performer gets a caution note and is re-dispatched → before/after comparison, all against the real Gateway, not a stub.

Full pipeline run: real, end to end

5 workers (meridian_cache, anchor_cdn, solace_queue, ridgeline_auth, cobalt_storage), each a real /v1/chat/completions call against the OpenClaw Gateway's real agent-backed endpoint, synthesized by a separate OllamaClient call and independently checked by the Verifier: 27 claims — 18 confirmed, 9 rejected, 0 unverified — plus a 1,878-character coherent briefing from the synthesis step. cobalt_storage came back at 0/4 confirmed, below the 80% caution threshold, and was selected as the worst performer for the feedback re-dispatch.

First blocker: every worker returned 0 claims

The very first full 5-worker run returned 0 claims from all 5 workers. Tailing the Gateway's own log (~/.openclaw-dev/gateway-managed.log) directly, rather than trusting the empty result, showed real, valid-looking JSON completions on every call — wrapped in a markdown code fence (```json ... ```) despite the system prompt asking for strict JSON. json.loads(raw) in OpenClawWorker.run() failed on every single one, silently swallowed by the existing except (json.JSONDecodeError, AttributeError): pass. A real agent turn does this; a raw Ollama json_mode=True call in this codebase never has.

Fix, validated cheaply before trusting it on a full re-run: added response_format: {"type": "json_object"} to the request payload, and a _strip_code_fence() regex helper applied before json.loads(). Checked first against the existing single-call smoke test (4 real claims back, no request error from the new field) before spending a full 5-worker batch on it — which then completed clean, producing the 27-claim result above.

The null result: a corrected prompt, an identical answer

cobalt_storage's caution-note re-dispatch came back identical to its original dispatch: 0/4 confirmed both times, and reading the Gateway log directly, the raw JSON text of the two responses was byte-for-byte the same. A changed system prompt produced no change at all in the output — not "a similar failure mode," the same characters.

Investigated rather than accepted: both passes used OpenClawWorker with the same worker_id, and at the time, _chat() built the Gateway's user field from worker_id alone (user=f"groundswarm:{task.worker_id}"). Per the integration page, user maps directly to a Gateway session key (sessionPrefix: "openai") — so both calls landed in the same ongoing OpenClaw agent conversation. The hypothesis: a same-session follow-up reads as a mid-conversation nudge, not a fresh instruction, and the agent anchors on repeating its first turn's answer rather than re-solving the task.

Tested directly with a control script using a different worker_id (hence a genuinely fresh Gateway session) but the exact same caution note present from the very first turn against the same source. Result: measurably different — 2/4 confirmed, and through a completely different failure mode entirely (the ADR-015-documented schema-echo dict-quote bug on the other 2, correctly caught and rejected by checks.py's existing str()-coercion rather than crashing). Fresh session, same note text, different output — the session, not the prompt content in isolation, is what the anchored retry was actually holding fixed.

Fix: a Gateway session per attempt, not per worker_id

OpenClawWorker now tracks a per-worker_id attempt counter (_attempts: dict[str, int]) and folds it into the Gateway user key: user=f"groundswarm:{task.worker_id}:{attempt}". The same worker identity's second dispatch now lands in a fresh Gateway session automatically — no manual worker_id renaming required, unlike the standalone control script above.

Re-validated in situ, through the actual product code path (not a hand-rolled diagnostic): cobalt_storage dispatched twice through one live OpenClawWorker instance, pass 2 carrying the same caution note the full pipeline run generated.

What this does and doesn't prove

The specific behavior change in pass 2 — every claim set quote: null rather than a fabricated span — is exactly what the caution note's text asked for ("leave quote null rather than guess at one"), which is suggestive that the note's content did something. But this is one sample, and it is confounded: pass 2 is both "cautioned" and "a fresh independent draw from the model," and only the fresh-session control test above isolated "session freshness changes the output" — nothing run so far isolates the caution note's own wording from a fresh, uncautioned re-roll happening to land on better quotes by chance.

Closing that gap needs a proper controlled comparison: fresh session, same source, WITH vs. WITHOUT the caution note, repeated enough times to move past n=1 — the same discipline ADR-014 already applied to the anti-echo prompt fix, and scoped here the same way, as follow-up work rather than a claim made now. What is established, not provisional: the same-session anchoring bug was real, reproduced live, root-caused to a specific mechanism (Gateway session reuse) rather than guessed at, and the fix removes it — the loop can now change a flagged worker's next output at all, which the first version of it, measurably, could not.
