Deterministic old-vs-new worker-prompt A/B

Question B from the Move-1 re-validation follow-up: did the ADR-009 worker-prompt change actually change extraction behavior, independent of dolphin3's sampling noise? Ten calls, temperature=0, one call per (source, prompt version) — run against a GPU-backed Ollama instance hosted on Google Colab (see infra note below).
The headline finding is a clean, positive, directly reproduced result: the single largest failure mode ADR-009 was built to fix — the worker echoing the schema's own placeholder text into the quote field instead of a real source quote — reproduces deterministically under the old prompt on 2 of 5 sources, and is completely absent from all 10 new-prompt claims across all 5 sources. That is a much stronger validation than the noisy 55-worker re-run could give, because it is a paired, controlled comparison: same source, same temperature, only the prompt text differs. Two real costs came with it: a genuine recall regression on some sources (the new prompt drops claims the old prompt caught), and one concrete instance of the computation field producing internally-inconsistent arithmetic that would cause the verifier to falsely reject a true claim.

Method

Reconstructed the exact old system prompt from git show HEAD:src/groundswarm/workers/sim_worker.py (pre-ADR-009) and paired it against the current working-tree prompt. For each of the 5 fixture postmortems, called OllamaClient.generate(..., temperature=0.0) once with each prompt version — 10 calls total, script at scratchpad, results archived alongside this run. At temperature=0 a call is a pure function of (prompt, source), so a repeat-count sweep would be redundant; one call per cell is already the full signal.

1. The exact bug ADR-009 targeted, reproduced and fixed — deterministically

On meridian_cache and ridgeline_auth, the old prompt's entire output for that call was one claim whose quote field is, character for character, the schema's own field-description text:
"quote": "a verbatim quote from the source supporting this claim, or null if none applies"
That is not a real quote from either postmortem — it is dolphin3 copying the instruction text itself, the exact failure mode the original 55-worker rejection analysis found in 10 of 29 rejections and that ADR-009's anti-echo instruction exists to stop. Under the new prompt, on the same two sources at the same temperature, none of the 7 resulting claims show this pattern — every quote is a real span that reads as copied from the source text. This is the cleanest possible evidence that the specific fix works: same input, same sampling, only the prompt wording changed, and the literal bug goes from 2/5 sources to 0/5.

2. The cost: a real recall regression, not just re-granularization

On the 3 sources where the old prompt was already producing real quotes (anchor_cdn, solace_queue, cobalt_storage), the new prompt did not simply re-word the same facts — it dropped some of them outright. Concretely:
  • anchor_cdn: the new prompt's 2 claims cover the API-token root cause and a duration; it drops the on-call paging/rollout timeline, the "100% of that hostname's traffic, other hostnames unaffected" scope claim, and the remediation plan (14-day alert, workload-identity flow) — all of which the old prompt captured with real quotes.
  • solace_queue: new drops the incident start time, the named root cause (slow downstream webhook receiver), and the "72-hour retention window never approached" claim.
  • cobalt_storage: new drops the root-cause claim (single storage node, failing disk) entirely, keeping only the impact/detection/remediation claims.
Where the new prompt's claim count also just dropped for a genuinely mechanical reason — e.g. solace_queue's lag and delay figures merged into one claim because the source itself contains them as a single sentence, and the new prompt's quote for that merged claim is a verbatim copy of that sentence, not a paraphrase — that's a legitimate consolidation, not a loss. But the three drops above are real content that no new claim, merged or otherwise, recovers. Net: the anti-echo fix is real and worked, but it did not come free — this is exactly the "false-rejection / coverage cost" ADR-012's Move-2 benchmark is scoped to measure formally, not something to iterate on ad hoc here.

3. New failure mode found: internally-inconsistent computation, on a claim that's true

The computation field was used exactly once across 10 new-prompt calls, on anchor_cdn's "The outage lasted for 34 minutes." claim:
operands: [{"value": "06:00 UTC on 2026-06-22", ...}, {"value": "06:19 UTC", ...}] operation: duration_minutes, claimed result: 34
Recomputing this exact operand pair with the verifier's own apply_operation() gives 19, not 34 — a straight mismatch that Verifier._check_computation would reject. But the underlying claim is almost certainly true: the source states "for 34 minutes" directly, and separately that rollout completed by 06:34 UTC (06:00→06:34 is also 34 minutes) — the postmortem's own prompt instructions even say "If the claim's number appears directly in the source, leave computation null and use quote instead," which this call violates by inventing a computation it didn't need. The worker picked the wrong second operand (06:19, the paging time, not 06:34, the rollout-complete time) but wrote the correct final number anyway, apparently copied from elsewhere in the source rather than actually derived from its own stated operands. Net effect: a true claim that the arithmetic check would falsely reject, caught here only because the deterministic A/B made the operand math checkable in isolation — in the noisy 55-worker run this would show up as one more computation rejection indistinguishable from the others already catalogued in Move 1 re-validation. Single instance so far; not enough to size the false-rejection rate on its own, but exactly the kind of case Move 2's benchmark needs a scored bucket for.

Infra note: Colab-hosted Ollama

Run against dolphin3 hosted on a free-tier Colab T4 GPU (not the local laptop), reached over a cloudflared quick tunnel via OLLAMA_HOST — see groundswarm/colab/ollama_colab_host.ipynb. Two infra issues hit and fixed along the way: Ollama's installer needs zstd, not preinstalled on the Colab image; and Ollama's own anti-DNS-rebinding Host-header check returns a bare 403 to any request through a tunnel unless the server is started with OLLAMA_ORIGINS=*. Separately, the free-tier GPU runtime was reclaimed mid-session (unsaved notebook, all state including the tunnel lost) after roughly the first 10–15 minutes of use, confirming the quota-reclaim risk this notebook's own setup instructions already warned about — worth budgeting for on any future run against this same infra.
